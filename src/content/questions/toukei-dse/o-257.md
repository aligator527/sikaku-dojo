  データ処理の各工程のログを記録するクラスを、次のように定義して実行した。

  ```python
  class Logger:
      history = []

      def __init__(self, name):
          self.name = name

      def log(self, msg):
          self.history.append(f"{self.name}:{msg}")

  a = Logger("a")
  b = Logger("b")
  a.log("start")
  b.log("stop")
  print(len(a.history), a.history is b.history)
  ```

  出力として正しいものを次のうちから一つ選べ。
choices:
  - '`1 False`'
  - '`1 True`'
  - '`2 False`'
  - '`2 True`'
  - '`AttributeError` が発生する。'
answer: 4
---
`history = []` はメソッドの外（クラス定義の直下）で代入されているので、インスタンスごとではなくクラスに 1 つだけ存在するクラス変数です。`self.history` はインスタンスに同名の属性がないためクラス変数を参照し、`append` はそのリスト自体を変更します。`a` と `b` は同じリストを共有しているので、`a.history` は `['a:start', 'b:stop']`（長さ 2）となり、`a.history is b.history` は `True` です。

### 各選択肢の検討

- ①：インスタンスごとに別のリストを持たせた場合に期待される結果です。そのためには `__init__` の中で `self.history = []` と代入し、インスタンス変数にします。
- ②：同じリストを共有しているので、`b.log("stop")` の記録も `a.history` に入り、長さは 2 です。
- ③：長さが 2 になるのは共有しているからで、その場合 `is`（同一のオブジェクトかどうか）は `True` になります。
- ④：正しい。
- ⑤：インスタンスに属性 `history` がなくても、属性の探索はインスタンス → クラスの順に行われるので、クラス変数が見つかりエラーにはなりません。

### ポイント

- クラス変数はすべてのインスタンスで共有される。変更可能な（ミュータブルな）オブジェクト（リスト・辞書など）をクラス変数にすると、意図しない共有が起こりやすい。
- `self.history = [...]` のように代入すると、インスタンスに新しい属性が作られ、以後はクラス変数を隠す。`append` のように中身を変更する操作は代入ではないので、クラス変数そのものが変わる。
- 同じ落とし穴に、関数の既定値に変更可能なオブジェクトを使う `def f(x, acc=[])` がある。既定値は関数の定義時に 1 回だけ作られ、呼び出しのたびに共有される。既定値は `None` にして、関数の中で新しいリストを作る。
- オブジェクト指向では、データ（属性）とそれを操作する手続き（メソッド）をまとめて扱う。状態をどこに持たせるか（クラスかインスタンスか）を意識することが、モジュール化・リファクタリングの基本になる。
