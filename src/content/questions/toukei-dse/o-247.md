  $n$ 件のアクセスログに含まれるユーザー ID の種類数を数えるため、次の 2 つの関数を用意した。

  ```python
  def count_unique_a(ids):
      seen = []
      for x in ids:
          if x not in seen:
              seen.append(x)
      return len(seen)

  def count_unique_b(ids):
      seen = set()
      for x in ids:
          if x not in seen:
              seen.add(x)
      return len(seen)
  ```

  ID がすべて異なる場合の計算時間について、正しいものを次のうちから一つ選べ。ただし、ハッシュ値の衝突は十分少ないものとする。

リストに対する `x in seen` は、先頭から順に要素を比べる線形探索で、`seen` の長さに比例する時間がかかります。ID がすべて異なると、$k$ 回目の判定では $k - 1$ 個と比べるので、合計 $0 + 1 + \cdots + (n - 1) = n(n - 1)/2$ 回の比較となり $O(n^2)$ です。集合（`set`）はハッシュテーブルで実装されており、`in` と `add` は平均 $O(1)$ なので、全体で平均 $O(n)$ です。

### 各選択肢の検討

- ①：リストの `in` は $O(\text{長さ})$ です。$O(1)$ で判定できるのは集合や辞書（ハッシュテーブル）です。
- ②：集合の `in` は、要素のハッシュ値から格納位置を計算して直接調べるので、順に比べる必要はありません。
- ③：リストは整列されているとは限らないので、`in` は二分探索ではなく線形探索です。
- ④：正しい。$n = 10^6$ なら、`count_unique_a` は約 $5 \times 10^{11}$ 回の比較が必要で現実的な時間では終わりませんが、`count_unique_b` は一瞬で終わります。
- ⑤：ハッシュ値の計算は要素 1 つにつき定数時間で、全体の計算量のオーダーを変えません。

### ポイント

- ハッシュテーブルの探索・挿入・削除は平均 $O(1)$。ただし衝突が多いと最悪 $O(n)$ になる。要素数とバケット数の比（負荷率）が大きくなると、テーブルを拡張して再配置する。
- 種類数を数えるだけなら `len(set(ids))` と書ける。各 ID の出現回数を数えるなら辞書や `collections.Counter` を使う。
- 集合や辞書のキーにできるのは、ハッシュ値が計算できる（変更不可能な）オブジェクトに限られる。リストはキーにできないが、タプルはできる。
